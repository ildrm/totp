# Vault and backup format v1

All strings are UTF-8. Binary values use canonical unpadded base64url. Unsupported versions and unexpected fields fail validation. `Envelope` fields are `version:1`, `suite:"A256GCM"`, `vaultId` UUID, `recordId` bounded string, `keyId` UUID, 12-byte `nonce`, and `ciphertext` with the 16-byte GCM tag appended by Web Crypto. Context must match the expected vault, key, and record.

AAD is the UTF-8 JSON encoding of `["still-vault",1,"A256GCM",vaultId,recordId,keyId]`. None of these fields contains an issuer, account, seed, tag, or note. A fresh CSPRNG nonce accompanies every seal. Changing any bound identifier requires decrypting and re-encrypting; storage migrations must never just rename an envelope.

A header carries `version`, optional `kind` (`personal` or `shared`), `vaultId`, `keyId`, creation date, Argon2id parameters, password and recovery wraps, and recovery salt. The random VEK is 32 bytes, imported as a non-extractable AES-GCM key. Password/recovery wraps use record contexts `password-key` and `recovery-key`. A password change creates a fresh salt and KEK and rewraps the existing VEK. It does not invalidate old backups or change OTP seeds.

Passphrases are NFC normalized. Creation requires 15–1,024 characters. Default Argon2id parameters are 65,536 KiB, three iterations, one lane, and a 16-byte random salt. Imported headers accept 19,456–262,144 KiB and two–ten iterations; unsupported workloads fail before running a KDF. Argon2 runs in a worker using hash-wasm. Passwords and mutable byte buffers receive best-effort clearing; JavaScript strings and garbage collection prevent an erasure guarantee.

Recovery uses an independent 32-byte random secret. Its displayed Base32 groups include a four-byte SHA-256 transcription checksum. The checksum detects typing errors and does not authenticate possession. HKDF-SHA-512 derives the recovery KEK using a random 16-byte salt and the exact recovery domain/vault context in `crypto.ts`. The recovery string is not uploaded or persistently stored in plaintext. Losing both passphrase and recovery/trusted-device access permanently loses encrypted data.

Records encrypt the full schema: ID, vault ID, schema version, issuer, account, normalized Base32 seed, RFC algorithm, digits, period/counter, color, favorite, folders, tags, notes, aliases, dates, usage, archive, and ordering. Settings are a separate encrypted record with ID `settings`; they stay device-local during sync. Structural IndexedDB migration from version 1 to 2 preserves envelopes. A legacy settings identifier can be migrated only after successful decryption.

The `.otpvault` JSON document contains `format:"still.otpvault"`, `version:1`, `header`, `records`, `manifest`, and `exportedAt`. The manifest’s record ID is `backup-manifest`. Its protected digest is SHA-256 over deterministic JSON of the entire header, ciphertext collection, and export date; object keys are recursively sorted, array order preserved. This detects dropped, reordered, substituted, and damaged records. V1 is the only released backup version; future incompatible versions fail safely until an explicit migration exists.

Limits: 9,999 accounts plus settings; 10,000 backup envelopes; 24 MiB restore file; 16,384 base64url characters per envelope ciphertext; 80 characters per envelope record ID. Restore verifies credentials, manifest, every AEAD, IDs, duplicates, and plaintext schemas before a transaction. Selective backups explicitly describe their reduced scope; restoring one replaces that vault’s contents, preserving other vaults.

Random 96-bit nonces provide probabilistic uniqueness. A 2^24 lifetime encryption budget is an operational rotation recommendation, not an enforced distributed per-key counter. High-volume deployments require independent nonce/key-use review and accounting. Fresh salts produce distinct password KEKs; explicit VEK rotation changes future ciphertext and recovery material. Old backups and previously disclosed OTP seeds remain accessible with old credentials.
