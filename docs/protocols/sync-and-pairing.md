# Authenticated sync, pairing, and shared vaults

Sync stores opaque vault, record, device, operation, and key IDs. An operation includes an idempotent UUID, vault/record IDs, base revision, envelope (or null for deletion), tombstone flag, and encrypted proof. Proof record context is `sync-op:<operationId>` under the current VEK. Its encrypted claim binds version, operation/vault/record IDs, base revision, deletion flag, and a canonical digest of the record envelope. A relay cannot fabricate a deletion or substitute content without a vault key.

The API locks the vault row before membership checks and writes. It preserves every competing operation, advances a monotonic revision, and changes a record head only when the submitted base equals its head revision. Reusing an operation ID with different content, proof, context, or device fails. Pull pages are bounded to 500 operations and expose only the current key epoch. History is capped at 100,000 operations per vault. Version changes are forward migrations, never automatic schema synchronization.

Clients persist pending encrypted operations before upload. Retries preserve operation IDs. Before applying a downloaded change, the worker authenticates the operation claim and record content/schema. Clients remember revision checkpoints, record heads, and operation/revision mappings; rollback, authenticated base mismatches, and renumbered replays fail. Acknowledged newer local state is not overwritten by older history. Conflicts remain encrypted locally and remotely. Explicit choices keep the local version, accept the remote version, or clone both under a new record ID. HOTP counter conflicts need deliberate reconciliation with the relying service; do not blindly choose the smaller counter.

These controls do not provide a global transparency log. A fresh device without a trusted checkpoint cannot prove completeness or freshness of server history. A compromised relay can withhold data, cause denial of service, present an old authentic history to a fresh device, and observe traffic sizes/timing. A party that obtains the group VEK can authenticate group operations; proofs attest key possession, not an individual device signature. Honest-server RBAC remains necessary, and a malicious viewer endpoint can extract shared seeds.

Pairing requests expire after three minutes. The recipient generates a non-extractable ECDH P-256 key in its worker and displays a QR/JSON proposal containing only public metadata. The authorized sender verifies the proposal through an out-of-band scan or transfer, locally reauthenticates, and performs a fresh cloud passkey verification. The relay checks device, membership, transaction, key epoch, public key, and expiry, then consumes approval once.

ECDH derives 256 shared bits. HKDF-SHA-256 uses the transaction UUID as salt and an explicit info tuple containing protocol, vault, sender, recipient, epoch, and expiry. AES-GCM wrap AAD additionally binds transaction and sender/recipient/epoch record context. Both sides display the first 64 bits of SHA-256 over the full transcript and both public keys, grouped in hexadecimal. The receiver must compare the fingerprint using the trusted sender screen before accepting; merely trusting the relay’s displayed identity is insufficient. The receiver locally wraps the received VEK with its own passphrase and new independent recovery key. No raw VEK or private device key reaches the relay.

Each shared vault has its own random VEK. Owner: read/write/invite/remove/delete. Admin: read/write/invite/remove non-admin members. Member: read/write. Viewer: read. Only owners promote admins, remove admins, or delete a shared vault. Removing the owner is forbidden. Membership checks occur on the backend and are tested independently of hidden buttons.

Rotation first synchronizes and resolves conflicts. The worker creates a new VEK, encrypted records, authenticated rotation operations, new wraps, and an encrypted recovery preparation. The API requires coverage of every live head, removes the chosen member, advances key ID/epoch, removes old key envelopes, and installs new encrypted heads atomically. The local commit checks the expected server key ID and opens the prepared header before replacing storage. A crash after server commit can resume the durable preparation with the old vault passphrase. Remaining devices must pair again. Keep a new backup and recovery kit after rotation; rotate external OTP setup keys separately to revoke previously copied seeds.

Revoking a device invalidates server sessions and future envelope retrieval. It does not erase offline seeds or backups already obtained. Deleting a cloud copy preserves local encrypted data; deletion of a local account is queued as an authenticated tombstone on the next sync. Re-enabling sync from old devices can create conflicts, so confirm intent on every trusted device.
