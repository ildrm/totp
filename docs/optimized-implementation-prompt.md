# Revised implementation specification

Build Still as a security product using a strict TypeScript pnpm monorepo, Next.js App Router PWA, NestJS API, and PostgreSQL. Preserve the existing GPL-2.0-only license. Use maintained platform primitives and libraries. Check release versions and compatibility, commit the lockfile, quarantine very recent packages, and audit production dependencies. Make every enabled capability functional and expose unsupported capabilities explicitly. Never equate generating code with validating a production release.

## Corrected requirements

The original specification combines an authenticator, encrypted sync, collaboration, an identity service, a developer MFA service, and an optional extension. These are distinct trust domains. Share OTP and validation code, never share consumer and verifier encryption keys. Cloud authentication cannot decrypt a personal vault. A third-party penetration test and authenticator hardware testing are external release gates; role-play does not satisfy them. Record feature coverage and real test evidence rather than making blanket completeness claims.

Select cryptography for its purpose. There is no single "most secure algorithm" that replaces encryption, hashing, password derivation, and OTP MACs. RFC 4226 uses HMAC-SHA-1; RFC 6238 permits HMAC-SHA-256 and HMAC-SHA-512. Preserve exactly provisioned parameters for existing accounts. Default manual imports to interoperable SHA-1/6/30; use SHA-256/8 and 256-bit seeds for new verifier enrollments, or SHA-512 and a 512-bit seed where the verifier explicitly supports it. Do not invent SHA-3/BLAKE3 OTP variants and label them interoperable. SHA-1 collision attacks do not directly imply a break of HMAC-SHA-1 OTP. The digit space, acceptance window, online attempt limits, seed theft, and phishing dominate OTP risk.

Encrypt consumer records using a random 256-bit vault key and Web Crypto AES-256-GCM, a fresh 96-bit nonce for every operation, a 128-bit authentication tag, and versioned AAD binding vault ID, record ID, key ID, and suite. Enforce operational key-use limits. A random nonce gives negligible collision probability under a usage budget, not a mathematical guarantee of uniqueness. Derive passphrase wrapping keys using Argon2id in a worker: default 64 MiB, three iterations, one lane, independent random 128-bit salt; reject imported work factors outside bounded limits. Never use a fast hash as a password KDF. Use a random independent 256-bit recovery secret, HKDF-SHA-512 with domain separation and vault binding, and an error-detection checksum that is explicitly not an authentication mechanism. Keys are non-extractable after import. JavaScript strings and GC do not permit guaranteed erasure.

Authenticate backup manifests with the vault key. The manifest must bind the header, entire ciphertext record collection, and export metadata using deterministic serialization. Per-record AEAD alone does not detect missing records. Validate sizes, versions, duplicate IDs, context, integrity, and decrypted schemas before transactionally replacing storage. Never overwrite a valid vault with an unverified partial import.

Keep long-lived plaintext seeds and keys in one crypto worker. Return metadata and requested codes only. Enrollment and explicit, recently reauthenticated reveal may briefly expose seeds to the UI. Lock terminates the worker and clears UI state; broadcast locks across tabs. Serialize mutations with Web Locks, and enforce an idle timer inside the worker as well as the UI. Favor a strong unsupported state over an unsafe storage-lock fallback. Backgrounding locks by default. HOTP increments only on explicit use, commits its counter before disclosure, and never increments just because it is displayed.

Use IndexedDB for encrypted records, settings, wrapped keys, and opaque sync state. Rebuild search indexes in memory. No secrets in localStorage, sessionStorage, cookies, caches, analytics, navigation URLs, logs, or server component payloads. No third-party fonts, favicon lookups, session replay, trackers, or remote QR decoding. QR images have format, size, and pixel limits. Scanning is user initiated and stops tracks on close. QR content is untrusted data; it is never navigated to. Strict provisioning parser rejects duplicate parameters, mismatched issuers, malformed encoding, unsupported algorithms, counter overflow, and excessive lengths.

Export a static Next.js shell to make offline availability independent of a Next.js server and authentication. Generate CSP hashes from final inline bootstrap scripts; self-only bundles and workers, no unsafe-inline or unsafe-eval, explicit wasm-unsafe-eval only for local Argon2 WebAssembly. Hashes support the immutable offline shell better than per-response nonces. Cache an explicit build-versioned asset allowlist only. Never cache API responses or runtime credential data. Show a controlled update action that locks before activation. HTTPS, HSTS, frame protection, no-referrer, restrictive permissions, nosniff, and same-origin opener isolation belong in the production deployment.

Cloud accounts use verified WebAuthn with required user verification, discoverable credentials, origin and RP-ID checking, one-time three-minute challenges, and multiple passkeys. Do not provide a recovery flow that bypasses cryptographic vault recovery. Protect opaque sessions in __Host cookies with Secure, HttpOnly, SameSite=Strict, absolute and idle expiration, rotation on login, and server-side revocation. Enforce Origin/Fetch Metadata and JSON content types on cookie-authenticated mutations. The independent developer API authenticates high-entropy scoped API keys. Distributed PostgreSQL-backed limits cover requests, challenges, verification, pairing, and sync. Proxy-aware IP handling must trust only known proxy hops; do not trust arbitrary forwarded headers.

Sync opaque IDs and encrypted envelopes only. Use database transactions for revisions, per-record optimistic concurrency, idempotent operation IDs, preserved conflict versions, tombstones, and access changes. Reject mismatched operation context and reused IDs with different payloads. Remember revisions locally and reject rollback. A fresh device without trusted history cannot prove the server presented the latest state. Never apply unauthenticated downloaded records over usable state. Preserve pending operations across retries, and provide explicit conflict resolution. Do not synchronize HOTP counters using naive last-write-wins.

Pairing uses separate ECDH P-256 device keys and HKDF with explicit protocol, transaction, vault, sender, recipient, expiry, and epoch binding. Authenticate the recipient's public key using an out-of-band QR or equivalent verified transfer. Authenticate the full transcript to prevent server key substitution; a server session alone does not make a relay trustworthy. Approval requires recent local and cloud verification. Expire and consume pairing transactions once. Revocation blocks future sessions and retrieval but cannot erase copied seeds. Rotate shared vault keys for future state, preserve exact membership permissions, and explain that viewers capable of generating codes can extract seeds on an untrusted endpoint.

The MFA verifier is optional and server-readable by design. Use a separate schema and KMS encryption context. Production must reject development keys and missing key management. Confirm possession before activation, never return seeds again, narrowly bound TOTP windows, compare candidates using timing-safe comparisons, and atomically track last accepted steps, HOTP counters, and consumed recovery-code hashes. Display random recovery codes and API keys once, store verifiers only, and require recent passkey verification for destructive administration.

## Product and design acceptance

Use a calm, legible UI whose shortest path is unlock → search → copy. Onboarding requires no account, a 15-character-or-longer passphrase, and a clearly explained independent recovery kit. Distinguish data recovery from password recovery. Show empty states rather than fake user accounts. Provide responsive navigation, visible keyboard focus, labels, native modal focus traps, reduced motion, high contrast, code grouping with ASCII digits and LTR isolation, and no live announcements every second. Provide local favorites, folders, archive, metadata search, usage sorting, expiration indication, configurable copy threshold, privacy mode, backup freshness, clock guidance, passphrase changes, and local deletion. Local-only mode must have the full core authenticator. Translate core flows in English, Persian, Arabic, Turkish, German, French, Spanish, Portuguese, Russian, Chinese, Japanese, and Korean; use logical CSS for RTL. State the precise translation scope.

## Verification and release gates

Run official HOTP vectors and all RFC 6238 SHA variants with the corrected 20/32/64-byte test seeds. Cover leading zeroes, boundaries, 2038+, unsigned 64-bit counters, T0, invalid periods, parser fuzzing, tampered AAD and ciphertext, nonce freshness, recovery transcription, passphrase changes, complete backup restoration, concurrent sync conflicts, IDOR, CSRF, challenge reuse, device revocation, verifier replay races, and recovery consumption. Test real production assets with enforced CSP, offline launch and OTP generation, storage inspection, QR image import, keyboard/modal behavior, mobile overflow, RTL, and automated accessibility checks. Verify positive and negative passkey proofs using virtual authenticators, then supported hardware. Run format, lint, type checks, dependency audit, reproducible builds, migration verification, Docker builds, secret scanning, SAST, SBOM and container scans. Track unrun tests explicitly. Independent cryptographic/application review, manual screen-reader testing, real cameras/passkeys, and deployed HTTPS restoration drills remain release gates until actually performed.

Produce documentation for architecture, crypto envelopes, threat model, sync, pairing, verifier API, privacy inventory, browser limits, operations, deployment, contribution, private security disclosure, and a requirement-to-evidence matrix. Report implemented behavior, test results, limitations, and outstanding release gates. Do not declare the entire platform production-ready while any mandatory implementation or validation gate is incomplete.
