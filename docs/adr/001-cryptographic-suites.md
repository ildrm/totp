# ADR 001 — Algorithm selection by purpose

Accepted 2026-10-04. "Newest" and "largest digest" are insufficient selection criteria. Interoperability, authenticated encryption, password resistance, vetted primitives, side channels, platform availability, and attack economics matter separately.

| Candidate              | Evaluation                                                                                                                                  | Decision                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| HMAC-SHA-1             | RFC 4226 baseline; existing provisioning compatibility. Collision weaknesses of unkeyed SHA-1 do not constitute a practical OTP HMAC break. | Preserve provisioned accounts; interoperability default for manual input.              |
| HMAC-SHA-256           | RFC 6238 alternative; native Web Crypto; broad mature support; enough MAC security for truncated OTPs.                                      | New verifier default with 256-bit secret and 8 digits.                                 |
| HMAC-SHA-512           | RFC 6238 alternative; largest standardized digest supported here; 512-bit seeds for generated accounts.                                     | Supported when service provisions it. No claim of 512-bit security for an 8-digit OTP. |
| SHA3-256 / SHA3-512    | Standardized FIPS 202 hashes with modern design; not RFC 6238 provisioning algorithms. Browser native support cannot be assumed.            | Evaluated, not substituted into OTP or AES.                                            |
| SHAKE256               | Extendable-output hash; arbitrary output size alone does not give a protocol definition or MAC.                                             | No custom OTP suite.                                                                   |
| KMAC256                | NIST SP 800-185 keyed MAC with explicit customization; credible future bespoke protocol candidate.                                          | No custom protocol: unsupported by existing OTP relying services.                      |
| BLAKE2b                | Mature fast hash, also used internally by Argon2. Fast generic hashes resist neither offline password guessing nor phishing.                | Used through the maintained Argon2id implementation, no custom seed/hash replacement.  |
| BLAKE3                 | Fast tree hash and keyed/KDF modes; extra implementation and compatibility costs without improving truncated OTP's dominant risks.          | No bespoke OTP or password KDF.                                                        |
| AES-256-GCM            | Native, standardized authenticated encryption with 128-bit tags; hardware acceleration; strict nonce budget required.                       | Record and key-envelope encryption.                                                    |
| XChaCha20-Poly1305     | Strong longer-nonce alternative; not widely available through native Web Crypto.                                                            | Future versioned-suite option after review; no silent downgrade.                       |
| Argon2id               | Memory-hard password KDF. 64 MiB/3/1 defaults exceed OWASP's 19 MiB/2/1 floor.                                                              | Password wrapping key only. Random VEK independent of passphrase.                      |
| HKDF-SHA-512 / SHA-256 | Domain-separated derivation from uniformly random recovery/ECDH input.                                                                      | Recovery wrapping / pairing wrapping respectively.                                     |

AES-GCM random 96-bit IVs have a birthday collision bound. Limit each VEK to 2^24 encryptions and rotate long before that on high-use installations. This release's 10,000-record and 100,000-server-history bounds are additional resource limits, not an enforced per-key nonce counter. Exact per-key usage accounting is a release gate for high-volume deployments. Revocation does not rotate external relying-service OTP seeds; those need separate rotation at the relying service.

References: [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226), [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238), [erratum 2866](https://www.rfc-editor.org/errata/eid2866), [FIPS 202](https://csrc.nist.gov/pubs/fips/202/final), [SP 800-185](https://csrc.nist.gov/pubs/sp/800/185/final), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html).
